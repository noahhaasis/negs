# iPhone: Leica Q3 60 MP DNG open / jetsam (2026-10-30)

## Reproduction and measurements

Fixture: `~/Downloads/3980774776.dng`, SHA-256 `bfb398233396e5f9c6c3b3b4069712609bdc913583d43d1e0427effbb2921d2e`, 73,114,690 bytes (69.7 MiB). TIFF SubIFDs: 9536 × 6344 14-bit CFA, 1620 × 1080 JPEG preview, **9520 × 6336 full-size JPEG preview**. Developed RAW: **9520 × 6336 = 60.3 MP** (native `decode_peak` confirms). A single RGB f32 image needs **690 MiB**; the 12 MP working copy needs **137 MiB**; 60 MP RGBA8 is 230 MiB. Compressed file size is not the working-set size.

Tested local `web/` build on USB-connected iPhone14,3 (iOS 26.6.2, Safari 26.6.1, WebGPU, four WASM threads), trusted local HTTPS, a *fresh* automation tab. Served the same Mac file via `web/serve.mjs` and opened it with `negs.open('results/3980774776.dng')`; this exercises the app's opening path but **not the native iOS Files picker**. `web/checks/footprint.py` sampled WebContent's physical footprint; live syslog confirms the kill. Artifacts in ignored `target/q3-iphone/` (`events.jsonl`, `footprint.jsonl`, `syslog.txt`, `zoom.log`, `export.log`, `open-after-export.log`, `desktop-open.log`). The file symlink and test servers were removed/stopped after testing.

Syslog at 13:09:20 local time: `memorystatus: killing_highwater_process pid 2550 [com.apple.WebKit.WebContent] ... 2223538KB`; `WebPageProxy::processDidTerminate ... reason=Crash`; `Process com.apple.WebKit.WebContent [2550] killed by jetsam reason highwater`. Earlier, at 13:07:02, the same process exceeded its *ActiveSoft 1536 MB* limit (nonfatal). The limit is pressure-dependent; don't treat 1536 MB or 2.2 GB as a fixed safe allocation ceiling. No JavaScript or WASM exception can catch an OS kill and display a graceful error afterwards. Peaks sampled every ~0.5 s may miss brief spikes. Other iOS WebKit processes (including networking and GPU) also use memory; the table is *one* WebContent process, not the whole phone.

Control: on macOS Chrome/WebGPU, the same file opens at its full 9520 × 6336 source size; initial frame 1814 × 1207; engine WASM high-water 1341 MiB. Native `target/release/examples/decode_peak` (allocator-instrumented) reports **999 MiB peak *above* the 70 MiB file buffer**, and 697 MiB still live after decoding, before any shrinking. Desktop WASM/WebGPU full-resolution export was **not** tested and is not established by successful open; browser WASM is limited to 4 GiB.

## Mechanism

- Touch-device `keptPixels()` limits the *retained* source and export to 12 MP. `decodeKept()` sends the whole file to `web/decoder.js` and `decode_photo()` in `crates/spektrafilm-wasm/src/lib.rs` calls `spektrafilm_io::load_raw_bytes_unoriented()` **at full size**, then `preview::downsample_area()`. The short-lived decoder saves *steady-state* engine memory, not the momentary decode peak. `web/app.js` keeps the original file bytes for future opens/restarts and passes them into the decoder again.
- `crates/spektrafilm-io/src/lib.rs::develop_rawler` and `vendor/rawler/src/imgop/develop.rs::develop_intermediate_owned` materialize a full-size f32 RGB frame after the raw mosaic. A single 690 MiB output plus the 115 MiB integer mosaic / 230 MiB float mosaic, file copies, downsized output, WASM growth/fragmentation, JS heaps and previously rendered GPU buffers explain the observed 1329 MiB decoder WASM and 1.7–2.2 GiB tab peaks. WASM `memoryBytes()` measures linear-memory high-water, **not** total physical footprint. The engine reports only 211 MiB after an open; it does not report the decoder or GPU/JS memory.
- This is a **memory-pressure/OS jetsam issue, not a corrupt Leica file or a GPU shader exception**. The first open can succeed in a fresh tab; after reuse/export, the same open can kill the tab. Real Files-picker use may add more transient memory; it was not measured here. The existing reduced-resolution export works in this test, but should not be called full 60 MP export.

## Routes to a fix (not implemented)

1. **Primary:** bounded RAW develop for constrained devices: decode the sensor, demosaic/calibrate in strips with enough Bayer-PPG halo, feed a downsampler, and keep only the ~12 MP result. Preserve RAW WB, orientation, crop and color, and check against today's full-develop-then-downsample pixels. Avoid materializing the 690 MiB full RGB intermediate. Merely lowering `MAX_PIXELS` or moving decode to another worker cannot remove that peak. Profile in WASM and on device; test repeated opens after exports, not just a fresh open. A smaller decoded working copy also helps later GPU/JS memory, but not this decode peak by itself.
2. **Graceful stopgap:** preflight *dimensions* from TIFF/DNG metadata before full decode (not just file bytes or the 720 × 480 IFD0 thumbnail), and on demonstrably constrained devices show a clear warning/option instead of risking OS kill. Offer a preview-only fallback from the embedded 1620 × 1080 or 9520 × 6336 camera JPEG; clearly label it **camera-processed JPEG, not developed RAW**, and constrain decode size before importing it. The current `placeholder()` already displays an embedded preview while RAW develops, but does not allow editing it as fallback. Because a fresh tab sometimes succeeds, unconditional rejection of all 60 MP files would be a usability regression; use a user-selectable safe mode or a memory-based policy once measured.
3. Reduce coexistence/retention: send bytes to the decoder with transfer/restore strategy, release obsolete bitmaps/GPU buffers, and avoid holding the previous export's allocations through another RAW decode. These save headroom but alone cannot guarantee a ~1.3 GiB decoder fits a phone under variable pressure. A JS `catch` around the existing decoder cannot recover from jetsam.

Desktop can use the full source; a Safari iPhone can intermittently open and edit/export a **12 MP working copy** today. For reliable full 60 MP processing, the native Mac app is the current route. Do not promise full-resolution browser exports without a separate memory/rendering test.
