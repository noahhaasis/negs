## Question and success criteria

`~/Downloads/3980774776.dng` (Leica Q3, 9520 × 6336 cropped, 60.3 MP; SHA-256 in the failure report) sometimes opens on the iPhone but kills its WebContent process on a later open after export. Existing touch code retains a 12 MP RGB copy, **but creates the full 690 MiB RGB image before downsampling it**. The short-lived worker's WASM high-water is 1329 MiB; WebContent peaked at ~1.7–2.1 GiB; syslog confirmed jetsam. On desktop the same file opens at full size. On the phone the current JPEG export is **12 MP**, not 60 MP; full-resolution browser export is a *separate* problem.

Build a prototype that produces the **same 12 MP working source from the actual RAW** without materializing full-size RGB. Keep full-size sensor decode if necessary for a first prototype; “streaming” here means bounded *development/demosaic + resampling*, **not necessarily streaming lossless-JPEG decompression or full-resolution export**. Compare on-device first-open and *open → reopen → zoom → export → reopen* footprint/latency with baseline, and report repeat runs and any kill. Aim for substantial headroom below the observed 1.5 GiB soft limit (not an invariant), rather than barely passing one fresh tab. Compare decoded pixel values with the existing implementation and show differences, especially near stripe boundaries, crop edges, WB, and highlights. Don't silently substitute the embedded JPEG: this experiment should process the RAW CFA.

**Normal 24 MP must not get slower by default:** initially gate the prototype to large Bayer RAWs on constrained/touch paths where `maxPixels > 0` and full-size exceeds a measured threshold (e.g. 40 MP); leave JPEG, 24 MP RAW, X-Trans and desktop (`maxPixels=0`) on the current code path. Force-enable/force-disable via an explicit benchmark-only switch for apples-to-apples comparisons, then decide on routing from results. If sharing/refactoring a common path, benchmark the *real* 24 MP control even when gated off. No claim of zero performance hit until measured. A 60 MP path may be slower per open because stripes and resampling do more bookkeeping; quantify it, not guess it.

## Exact path to replace

`web/app.js` `keptPixels()` / `decodeKept()` → `web/decoder.js` (`module.decode(bytes, maxDim, maxPixels)`; reports `decodeMs`, `readyMs`, `memoryMiB`) → `crates/spektrafilm-wasm/src/lib.rs` `decode_kept` / `decode_photo`. The latter calls `spektrafilm_io::load_raw_bytes_unoriented` → `develop_rawler` in `crates/spektrafilm-io/src/lib.rs`, then `preview::downsample_area(&image, target)` from `crates/spektrafilm-core/src/preview.rs`, then orients the **small** result. `kept_size()` in WASM computes the target based on the *cropped* decoded dimensions. Leave the normal `Engine::load`/desktop path and JS handoff unchanged if possible; add a dedicated `spektrafilm-io` bounded-develop API (or narrow WASM wrapper) returning small image **plus full cropped size and orientation**, and use it only when supported and selected.

Within `develop_rawler`: `rawler::decode` builds the sensor mosaic, `white_balance::prepare` updates WB metadata, `RawDevelop::develop_intermediate_owned` (`vendor/rawler/src/imgop/develop.rs`) applies sensor scaling, PPG demosaic and crop, then Negs's `calibrate` and `white_balance::finish` develop linear RGB. `flatten_rgb` transfers the full RGB allocation in f32 builds. The existing code avoids an extra *clone* of the sensor, but still needs full RGB before shrinking. The DNG holds a 9536 × 6344 Bayer CFA and uses a *single* lossless-JPEG strip: the first version can let rawler decompress the whole ~115 MiB u16 mosaic, and optionally create a ~230 MiB scaled f32 mosaic. Do **not** assume `RowsPerStrip` gives independently decodable tiles. `RawSource::new_from_slice` itself copies file bytes (~70 MiB); avoid making more copies while prototyping, but treat that as a separate optimization.

Native allocator-instrumented baselines (`target/release/examples/decode_peak`): Q3 file 70 MiB, RGB 690 MiB, **999 MiB peak above the file buffer**, ~796 ms in that isolated run. Controls: `web/results/sony.arw` (4000 × 6000 = 24 MP Bayer, 275 MiB RGB, 580 MiB native decode peak above 24 MiB file, ~204 ms); `web/sample/DSC_6377.dng` (6048 × 4032 = 24 MP *linear RGB* DNG, 279 MiB, 568 MiB above 3 MiB file, ~176 ms); `web/results/0955097116.raf` (6240 × 4160 = 26 MP X-Trans; prior on-device control). These are **one-run native numbers**, not phone/worker timing or an agreed performance budget; rerun in paired repetitions.

## Suggested implementation sequence

1. **Baseline before edits**: record hashes/build identity, output size, pixel checksum, native allocator peak and median/p95 timings (warm/cold separately) for Q3 + both 24 MP controls. Build matching WASM JS and measure `decoder.memoryMiB`, worker `decodeMs`, total opening/first frame, WebContent sysmon peak and whether the phone survives the sequence above. Use a fresh tab for each A/B sequence; repeat each sequence, don't compare a warmed baseline against a cold prototype. Cache the baseline build/results outside source-controlled assets.
2. **First bounded path, Q3 Bayer only.** Keep the full mosaic and its metadata, compute the *global* demosaiced cropped rectangle, target dimensions (same `kept_size` rounding), original-orientation policy, WB and calibration transform. Process horizontal full-width strips/rows with overlap sufficient for PPG, not independent rectangular JPEG blocks. Pass each calibrated interior row (or a bounded group) directly to an incremental reducer that implements the current `downsample_area` source→target fractional spans/order. Write directly into the final target RGB image, not another 60 MP intermediate. Release strip buffers before moving on. Preserve scalar f32 and clamping/highlight behavior. If an initial experiment uses full-height f32 mosaic, say so: bounded output still removes the full RGB allocation.
3. **PPG seam/crop correctness is hard:** `vendor/rawler/src/imgop/sensor/bayer/ppg.rs` performs sequential border, green, red/blue-at-green and red/blue-at-non-green passes, with later passes depending on earlier neighbors. A two-pixel halo is *not* necessarily enough across all passes. Prototype with a generous 8–16-row halo, then determine/prove the minimum empirically with tests. Pass original CFA phase and active-area offsets into each strip: calling PPG on a cropped strip without shifting CFA (`cfa.shift`) or including global image borders gives periodic color errors and visible horizontal seams. Ensure strip interiors never use PPG's artificial border interpolation, except at actual image edges. Avoid cloning the whole `RawImage`/mosaic per strip. Review `RawDevelop::develop_intermediate_owned` crop rules (`CropActiveArea`, `CropDefault`, `crop.adapt`) and `calibrate`/`white_balance::finish` for pixel-equivalent ordering. A separate bounded Bayer-specific kernel can be easier to validate than repeatedly calling the full developer with fake tile metadata.
4. **Test from the core out.** Use synthetic Bayer images of odd/even dimensions, RGGB variants, nonzero active/default crops, every boundary and multiple stripe heights, different target dimensions, EXIF rotations 1–8, WB modes and clipped highlights. Compare the bounded target with **full `load_raw_bytes_unoriented` then the existing `preview::downsample_area`, then orientation** using identical span math. Test hashes or finite-valued pixel deltas, max/mean error and a per-row heat map, especially at stripes and edges. Aim for exact output where practical; document any tolerance/algorithm difference rather than hiding it. Use real Q3 pixel comparisons; avoid committing its proprietary RAW. Unsupported DNG variants (linear raw, 4-color, X-Trans, odd crop/metadata) must take a defined *safe* path, not a silent inaccurate one or unsafe 60 MP full-develop fallback on the phone.
5. **Only then connect the feature flag in WASM**, build `web/pkg` and `web/pkg-threads` with `web/build.sh --threads` per repo setup, compare `module.decode()` results and rerun repeated-open/zoom/export tests on the physical iPhone; confirm subsequent editing, original view, rendered pixels and export are still healthy. If memory remains high, instrument WASM checkpoints around raw decode, scaling, each stripe and reducer; `memoryBytes()` is high-water, not live heap. The JS page's original file, decoded worker, GPU/renderer and file-picker may dominate the next peak. Consider `RawSource` file-byte copy and WASM/JS transfer only after profiling. If the worker or tab dies, the prototype is not a pass even if a fresh tab works.
